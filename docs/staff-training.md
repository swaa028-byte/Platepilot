# Staff training and pilot acceptance

Use one consenting restaurant with its actual menu, hours, payment setup and measured floor plan. Never create a fictional pilot.

## Host and server

Sign in with a work email. Confirm the assigned location. Open Live Floor in 2D, identify table states by text as well as color, select a table and open its service panel. Opt into 3D only if useful; confirm Switch to 2D remains available. Practice a reservation, walk-in, table move and split check. Keyboard users must be able to reach every table and control.

## Kitchen

Confirm station routing and item notes. Advance a new ticket to preparing, ready and served; practice bump/recall and reconnect after network loss. Verify duplicate provider notifications still produce one ticket. Print through the verified browser path.

## Manager

Review the imported menu before publication. Confirm service hours, delivery zones, currency and payment environment. Open and close a cash shift, investigate a discrepancy, request a partial refund and reconcile it after provider confirmation. Export totals separately by currency. Review consent before any marketing action.

## Pilot checklist

- Empty setup contains only merchant-entered records.
- Correct Google branch or manual setup is confirmed; ownership is independently reviewed.
- Real menu, operating settings and measured floor plan are approved.
- Test-mode order → verified payment → exactly one ticket → fulfillment → receipt → refund → reconciliation passes.
- Staff complete a shift without developer database edits, including Arabic and keyboard checks where required.
- Test transactions are labeled and excluded from live reports.

Only authorized staff sign-off changes the release to PILOT ACCEPTED. LIVE requires a separate explicit approval.
